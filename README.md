# Fairway: a HighwayHash Rust port

Repo layout: the publishable library lives in [`crates/fairway-hash`](crates/fairway-hash)
(published on crates.io as `fairway-hash`), dev automation in `xtask/`; the root
`Cargo.toml` is a virtual workspace manifest.

[![ci](https://github.com/juanmaneo/fairway/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/juanmaneo/fairway/actions/workflows/ci.yml)
[![License: Apache-2.0](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

A zero-dependency Rust port of Google's
[HighwayHash](https://github.com/google/highwayhash) (64/128/256-bit) and its
companion SipHash-2-4 / SipHash-1-3 and SipTreeHash.

HighwayHash is a strong pseudorandom function with
[security claims](https://arxiv.org/abs/1612.06257) — about 4x faster than
SipHash and 10x faster than BLAKE2. This crate reproduces the exact, frozen
output of the upstream C++ library and is verified against its golden test
vectors (all input sizes 0..=64 for 64/128/256-bit hashes, the SipHash
reference vectors, and the streaming "cat" equivalence test) on every backend.
Upstream publishes no SipTreeHash vectors, so those were generated by
compiling the upstream C++ reference; every implementation (AVX-512VL, AVX2,
NEON and portable) reproduces them.

## Backends

| Backend | Platforms | Selection |
|---|---|---|
| AVX-512VL | x86_64 | runtime-detected; off-by-default `avx512` feature (needs Rust 1.89+ when enabled) |
| AVX2 | x86_64 | runtime-detected |
| SSE4.1 | x86_64 | runtime-detected |
| NEON | little-endian aarch64 | always available |
| Portable (scalar) | everything else, incl. big-endian | fallback / `scalar` module |

The table is for HighwayHash. `sip_tree_hash` has an AVX2 version (runtime-detected,
about 1.7x the portable one on large inputs) and a portable one, like upstream,
plus a NEON one on little-endian aarch64 that upstream does not have (two
chains per 128-bit register; checked against the portable code, but not yet
benchmarked on real hardware). With the `avx512` feature, CPUs that have
AVX-512VL use a third version, also new. On an Intel Xeon 6985P-C it is 7%
faster than the AVX2 one on 32-byte inputs and 43-56% faster from 1 KiB up;
other AVX-512 CPUs are unmeasured, and `cargo run --release --example bench`
with and without `--features avx512` compares them. Every other CPU uses the
portable one.

## Usage

```rust
use fairway_hash::{HighwayHasher, Key};

let key = Key([1, 2, 3, 4]);

// Incremental (streaming) hashing:
let mut h = HighwayHasher::new(key);
h.update(b"hello ");
h.update(b"world");
let h64: u64 = h.finalize64();
let h128: [u64; 2] = h.finalize128();
let h256: [u64; 4] = h.finalize256();

// One-shot helpers (best backend for the current CPU):
use fairway_hash::{fairway64, fairway128, fairway256};
assert_eq!(fairway64(key, b"abc"), fairway64(key, b"abc"));

// Many small inputs with one key: build the hasher once (key schedule and
// CPU detection done once), then hash each input from it (about 1.5x faster
// than `fairway64` under 1 KiB):
let keyed = HighwayHasher::new(key);
assert_eq!(keyed.hash64(b"packet"), fairway64(key, b"packet"));

// Many independent inputs at once (about 1.4x faster than a loop on large
// inputs, 2x on tiny ones; `_par` also uses several threads for big batches):
use fairway_hash::{fairway64_many, fairway64_many_par};
let inputs = [&b"alpha"[..], b"beta", b"gamma"];
let mut out = [0u64; 3];
fairway64_many(key, &inputs, &mut out);
assert_eq!(out[1], fairway64(key, b"beta"));

// Force a specific backend (e.g. for cross-checking):
use fairway_hash::{Backend, HighwayHasher};
let mut h = HighwayHasher::with_backend(key, Backend::Portable);
h.update(b"abc");

// SipHash (matches the reference implementation byte-for-byte):
use fairway_hash::{sip_hash, sip_hash13, SipHashKey};
let k = SipHashKey([0x0706050403020100, 0x0F0E0D0C0B0A0908]);
let mac = sip_hash(k, b"message");
let mac13 = sip_hash13(k, b"message");

// SipTreeHash: SipHash with a 256-bit key over four interleaved chains
// (SIMD where available, portable otherwise), plus the reduction it ends with:
use fairway_hash::{reduce_sip_tree_hash, sip_tree_hash, Key};
let tree = sip_tree_hash(Key([1, 2, 3, 4]), b"message");
let combined = reduce_sip_tree_hash(k, &[tree, 42]);
```

## C ABI

`crates/fairway-capi` exports the functions of upstream's `c_bindings.h`
(`SipHashC`, `SipHash13C`, `HighwayHash64` and the `HighwayHash64_Target*`
family) under the same names; the header is
`crates/fairway-capi/include/fairway_capi.h`. It is not published to crates.io.
Build the libraries with `cargo build --release -p fairway-capi` and link
`target/release/libfairway_capi.a` or `.so`. A `_Target*` function whose
instruction set is missing returns the portable result instead of crashing;
fairway has no VSX backend, so `HighwayHash64_TargetVSX` is the portable code.

## Notes

- The key should be random and secret; attackers who know the key can forge
  hashes.
- Streaming semantics match C++ `HighwayHashCatT`: hashing `["A", ""]` equals
  `["", "A"]`. Append a length or non-empty marker per field if you hash
  independent fields.
- `no_std` is supported via `default-features = false`.
- `scalar::sip_tree_hash` always runs the portable tree hash, whatever the CPU.
- Build with `--features portable-only` to force the scalar backend on x86_64
  (useful for testing).
- `HighwayHasher::with_backend` falls back to the portable backend when the
  requested one is not supported by the CPU/build; `backend()` reports the one
  in use.
- Without `std`, SIMD backends are only used when enabled at compile time
  (e.g. `-C target-feature=+avx2`), since runtime detection needs `std`.
- MSRV: Rust 1.88 (the off-by-default `avx512` feature needs 1.89+ when enabled).

## Performance

On a Zen 3 laptop with the AVX2 backend, one-shot hashing runs at about
6.5-7 GiB/s on large inputs, and `fairway64_many` at about 9.5 GiB/s. Hashing a
*single* input is a serial chain and cannot be spread over threads; the
`fairway*_many` functions interleave several independent inputs instead, and
`fairway*_many_par` adds threads (`std` feature, no dependencies) once a batch
holds a few MiB per thread. Run `cargo run --release --example bench`
to measure your own machine.

No special build flags are needed: the SIMD backends enable their CPU feature
on every function, so they are inlined with the default release profile.
Link-time optimization (`lto = true`) or `-C target-cpu=native` still help a
little on very small inputs.

## Development

Run from the repo root before every push (CI runs the same command):

```sh
cargo xtask dev-check   # fmt, clippy + tests on every feature set, rustdoc, coverage
cargo xtask coverage    # coverage gate only; add --html for target/llvm-cov/html
```

Coverage needs `rustup component add llvm-tools && cargo install cargo-llvm-cov`.

Or use the dev container, which has the whole toolchain (Podman, Buildah or
Docker; with rootful Docker add `--user "$(id -u):$(id -g)"`):

```sh
podman build -t fairway-dev .
podman run --rm -it -v "$PWD":/work:Z fairway-dev                  # cargo xtask dev-check
podman run --rm -it -v "$PWD":/work:Z fairway-dev cargo xtask coverage --html
```

Container builds go to `target/container/`, apart from host builds.

To test the NEON backend from an x86_64 machine with `qemu-aarch64`:

```sh
rustup target add aarch64-unknown-linux-musl
CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_LINKER=rust-lld \
CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_RUNNER=qemu-aarch64 \
  cargo test --target aarch64-unknown-linux-musl --package fairway-hash
```

The tests port the upstream C++ suite: `tests/highwayhash_test.rs`
(`highwayhash_test.cc`: golden vectors and `HighwayHashCat` on every backend),
`tests/sip_hash_test.rs` (`sip_hash_test.cc`) and `tests/fuzz_test.rs`
(deterministic versions of the two libFuzzer targets, cross-checking every
backend against the portable one). Upstream's `vector_test` and
`data_parallel_test` cover C++ vector classes and a thread pool, which this
port doesn't have.

To test a big-endian target from an x86_64 machine with `qemu-ppc64`. Only the
portable code runs there, so byte-order mistakes show up as wrong hashes (the
NEON backends are built for little-endian aarch64 only). The `crt-static`
flags are needed because this target links dynamically by default:

```sh
rustup target add powerpc64-unknown-linux-musl
CARGO_TARGET_POWERPC64_UNKNOWN_LINUX_MUSL_RUSTFLAGS="-C target-feature=+crt-static" \
CARGO_TARGET_POWERPC64_UNKNOWN_LINUX_MUSL_RUSTDOCFLAGS="-C target-feature=+crt-static" \
CARGO_TARGET_POWERPC64_UNKNOWN_LINUX_MUSL_LINKER=rust-lld \
CARGO_TARGET_POWERPC64_UNKNOWN_LINUX_MUSL_RUNNER=qemu-ppc64 \
  cargo test --target powerpc64-unknown-linux-musl --package fairway-hash
```

### Fuzzing

[`fuzz/`](fuzz) has four libFuzzer targets: `highwayhash`, `sip_hash`,
`sip_tree_hash` and `batch`. They are differential: every backend the CPU
supports is compared with the portable code (and `sip_hash` with an
independent SipHash written from the spec and with `std`'s), over random
keys, lengths, alignments and streaming splits. They run under
AddressSanitizer on exact-size allocations, so an out-of-bounds read in a
SIMD load is reported. The crate has its own workspace, so the main build
stays dependency-free and offline.

It needs a nightly toolchain and `cargo-fuzz`:

```sh
cargo install cargo-fuzz
cargo +nightly fuzz run --fuzz-dir fuzz -a highwayhash              # or sip_hash, sip_tree_hash, batch
cargo +nightly fuzz run --fuzz-dir fuzz -a highwayhash -- -max_total_time=60
cargo +nightly fuzz run --fuzz-dir fuzz --features avx512 -a sip_tree_hash   # needs an AVX-512 CPU to cover it
```

A run goes on until it finds a failure or you stop it; `-a` turns on debug
assertions. Keep `-max_len` at 4096 or more (the default) for `batch`, which
needs long inputs to reach its interleaved path. `tests/fuzz_test.rs` is the
deterministic stand-in that runs in CI.
