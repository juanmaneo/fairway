## [Unreleased]

## [0.1.2] - 2026-11-14

Feature and fix release. Hash output is unchanged wherever it was correct
(big-endian aarch64 now returns the correct value) and the public API only
grows.

### Changed

- Small inputs on the AVX2 backend are fast without link-time optimization.
  The backend's `new`, `update_remainder` and `finalize*` functions now carry
  `#[target_feature(enable = "avx2")]` themselves, so the compiler inlines them
  into the entry points with the default release profile. Measured on a Zen 3
  laptop with `lto = false`: a 32-byte hash went from about 32 MiB/s to about
  450 MiB/s, a 1 KiB hash from about 0.9 GiB/s to about 4.2 GiB/s, and large
  inputs are unchanged (about 5 GiB/s). With LTO enabled nothing changes. The
  0.1.1 "Known limitations" note no longer applies. Hash output is unchanged.
- `fairway*_many` interleave six inputs instead of four. Measured on Zen 3
  (AVX2) against four and eight lanes, six was about 5-8% faster on inputs
  of 1 KiB and up, and eight was slower than four.

### Added

- `SipHashState` and `SipHash13State` (both `SipState<U, F>`): the public
  incremental SipHash state of upstream `SipHashStateT`, with `new`, `update`
  (one 8-byte packet), `update_bytes` (a whole message with SipHash padding,
  upstream `UpdateState`), `finalize` and `Clone`. `sip_hash` and `sip_hash13`
  now run on it. Hash output is unchanged.
- `crates/fairway-capi`: a C ABI with the entry points of upstream
  `c_bindings.h` under the same names (`SipHashC`, `SipHash13C`,
  `HighwayHash64` and `HighwayHash64_Target{Portable,SSE41,AVX2,VSX}`), plus
  `HighwayHash64_TargetNEON`, and the header `include/fairway_capi.h`. It is a
  separate, unpublished crate (`cargo build --release -p fairway-capi` makes
  the static and shared libraries), so `fairway-hash` stays free of `extern`
  functions. Differences from upstream: a `_Target*` function whose
  instruction set is missing returns the portable result instead of crashing,
  keys need no alignment, and `_TargetVSX` is always the portable code
  (fairway has no VSX backend). Checked against the golden vectors from Rust
  and from a C program linked against the static library.

- `sip_tree_hash`, `sip_tree_hash13`, `reduce_sip_tree_hash` and
  `reduce_sip_tree_hash13`: ports of upstream `SipTreeHash` /
  `ScalarSipTreeHash` and `ReduceSipTreeHash` (`sip_tree_hash.h`,
  `sip_tree_hash.cc`, `scalar_sip_tree_hash.cc`). SipHash-2-4 (or 1-3) with a
  256-bit key over four interleaved chains, one per 8-byte word of each
  32-byte packet, reduced to one 64-bit hash. On x86_64 CPUs with AVX2 (found
  at runtime, as for the HighwayHash backends) the four chains are the lanes
  of one 256-bit register: about 1.5x the portable code on 32-byte inputs
  and 1.7x from 1 KiB up (6.1 against 3.5 GiB/s on large inputs, one Zen 3
  core), and about 1.9x plain `sip_hash`. On little-endian aarch64 a NEON
  version runs two chains per 128-bit register; upstream has no NEON tree
  hash, so this is new code, checked against the portable code (under qemu)
  but not yet benchmarked on real hardware. With the off-by-default `avx512`
  feature (Rust 1.89+), CPUs with avx512f+avx512vl+avx512bw run an AVX-512VL
  version instead of the AVX2 one: the same four lanes in one 256-bit
  register, with single-instruction rotates (`_mm256_rol_epi64`) and a masked
  load for the final packet. Also new code with no upstream counterpart: it
  is the AVX2 code with instruction substitutions. Its tests (all lengths
  0 to 160 against the portable code, plus the golden vectors) pass on an
  Intel Xeon 6985P-C. There it is faster than AVX2 at every size, unlike the
  AVX-512VL HighwayHash backend below. Throughput of the `tree best` column
  of `cargo run --release --example bench` (one pinned core, LTO on), AVX2
  to AVX-512VL: 32 bytes +7%, 64 bytes +19%, 1 KiB +43%, and +50% to +56%
  from 64 KiB up (about 5.2 to 7.9 GiB/s on 1 MiB). With LTO off the gain is
  +20% at 32 bytes and +57% at 1 MiB. Other AVX-512 CPUs are unmeasured;
  comparing `cargo run --release --example bench` with and without
  `--features avx512` shows whether it also wins there. Other CPUs use the
  portable code; the result is the same everywhere.
  `scalar::sip_tree_hash` and `scalar::sip_tree_hash13` always run the
  portable code, for cross-checking. Upstream ships no golden values for the
  tree hash, so the tests use values generated by compiling the upstream C++
  reference (19 input lengths from 0 to 65536 for both variants, plus the
  reduction), run through every implementation, and a fuzzer cross-checks the
  SIMD code against the portable code on every length up to 159 bytes and on
  random keys, lengths and alignments.
- The benchmark example (`cargo run --release --example bench`) has a
  SipHash section comparing `sip_hash`, the portable and the best
  `sip_tree_hash`, and `fairway64`.
- `HighwayHasher::hash64`, `hash128` and `hash256`: hash an input starting
  from the hasher's current state without modifying it. On a fresh hasher
  this equals the one-shot functions with the key schedule and CPU detection
  done once, which is about 1.5x faster for inputs under 1 KiB when many
  inputs share one key (22 million 32-byte hashes per second on one Zen 3
  core, against 15 million for `fairway64`).
- Optional AVX-512VL backend on x86_64 behind the new off-by-default `avx512`
  cargo feature: the AVX2 algorithm re-encoded with EVEX instructions on
  256-bit registers (`_mm256_rolv_epi32`, `_mm256_ternarylogic_epi32`,
  `_mm256_maskz_loadu_epi8`). Selected at runtime when
  avx512f+avx512vl+avx512bw are detected, forcible with
  `HighwayHasher::with_backend(_, Backend::Avx512)` (falls back to portable
  where unsupported). Hash output is unchanged: the golden vectors pass on
  AVX-512 hardware, and the fuzzer cross-checks it against the portable
  backend. Enabling the feature requires Rust 1.89+, where the AVX-512
  intrinsics and target features were stabilized; the crate's MSRV stays
  1.88 without it. Measured on a Xeon 6985P (one core, LTO
  off, 64 MiB per run, hyperfine, 15 runs): not a win for the common one-shot
  path there — `fairway64` on 32-byte inputs is about 25% slower than AVX2
  (64 vs 81 ms per 64 MiB), about 10% slower at 1 KiB, equal at 1 MiB — and
  `fairway64_many` is much slower on 32-byte batches (46 vs 71 ms) but about
  18% faster on 1 KiB batches (43 vs 36 ms). It therefore stays opt-in; AVX2
  remains the default choice on this hardware.
- libFuzzer targets in `fuzz/` (its own workspace, so the library stays
  dependency-free): `highwayhash`, `sip_hash`, `sip_tree_hash` and `batch`.
  They are differential, checking every backend the CPU has against the
  portable code, `sip_hash` against an independent SipHash and `std`'s, and the
  `fairway*_many` functions against single hashing, over random keys, lengths,
  alignments and streaming splits, on exact-size allocations under
  AddressSanitizer. Run with `cargo +nightly fuzz run --fuzz-dir fuzz -a
  <target>` (add `--features avx512` on an AVX-512 machine). Short runs
  of all four found nothing; deliberately injected bugs (an off-by-one in
  `update`, a dropped packet in the batch lockstep path or in the scalar tree
  hash for one length, a one-byte over-read) were each found in a run capped
    at 60-90 seconds.
  `tests/fuzz_test.rs` stays as the deterministic stand-in for CI.

### Fixed

- The NEON HighwayHash backend is now used only on little-endian aarch64.
  It was selected on every `target_arch = "aarch64"` target, including
  big-endian ones (`aarch64_be`), where its lane loads read the input in the
  wrong byte order and `fairway64` and friends returned wrong hashes (for
  100 bytes `0..99` under key `[1, 2, 3, 4]`: `3e3fd06ecc830535` instead of
  `56b739f979c440f9`). Found by running a freestanding probe under
  `qemu-aarch64_be`. Big-endian aarch64 now falls back to the portable
  backend, which gives the correct value; `Backend::Neon` still exists on
  every target and falls back to portable where unsupported. Little-endian
  aarch64 is unchanged.

## [0.1.1] - 2026-11-13

Performance release. Hash output is unchanged and the public API only grows.

### Changed

- Much faster AVX2 and SSE4.1 backends. The `core::arch` intrinsics were
  being called out of line because the calling code did not enable the
  matching CPU feature, which made AVX2 slower than the portable code. The
  hot path now goes through `#[target_feature]` entry points that let the
  compiler inline the whole update loop. On a Zen 3 laptop, AVX2 throughput
  on large inputs went from about 150 MiB/s to about 6.9 GiB/s, and a 32-byte
  hash from about 26 MiB/s to about 1 GiB/s. Hash output is unchanged.
- `HighwayHasher::update` dispatches on the backend once per call instead of
  once per 32-byte packet, and no longer copies the completed packet through
  a temporary buffer.
- `fairway64` / `fairway128` / `fairway256` feed whole packets straight from
  the input and the tail straight into finalization, instead of going through
  the incremental hasher and its 32-byte buffer.

### Added

- Batch hashing of many independent inputs: `fairway64_many`,
  `fairway128_many` and `fairway256_many`. A single hash is a serial chain,
  so the CPU idles between steps; four inputs are advanced together to fill
  those gaps. Output is identical to calling the one-shot functions in a
  loop, and any byte-like input type works (`&[u8]`, `Vec<u8>`, `String`).
  On a Zen 3 laptop this is about 1.4x faster than a loop for inputs of
  several KiB and larger (9.5 GiB/s against 6.9 GiB/s), 1.2-1.5x from 256
  bytes to a few KiB, and about 2x for inputs of 64 bytes or less (one key
  schedule for the whole batch).
- `fairway64_many_par`, `fairway128_many_par` and `fairway256_many_par`
  (`std` feature): the same, spread over scoped threads when the batch is
  large enough to pay for them (16-24 GiB/s on a 16-thread laptop for batches of
  16-128 MiB, against 6.8 GiB/s for a loop). The crate still has no dependencies.
- `examples/bench.rs`, a zero-dependency throughput benchmark
  (`cargo run --release --example bench`).

### Known limitations

- The speedups above assume the compiler inlines the AVX2 / SSE4.1 backends
  into the entry points. That always happens for the update loop (large
  inputs reach about 6.5 GiB/s with the default release profile), but for
  *small* inputs on AVX2 the finalization code is only inlined with link-time
  optimization (`lto = true`) or `-C target-cpu=native` / `-C
  target-feature=+avx2`. Without either, a 32-byte AVX2 hash still runs at
  about 30 MiB/s, as in 0.1.0. Applications that hash many small inputs
  with the AVX2 backend should enable one of them.

## [0.1.0] - 2026-11-12

Initial release: a zero-dependency Rust port of Google's HighwayHash.

### Added

- `fairway-hash`: 64/128/256-bit HighwayHash and SipHash-2-4 / SipHash-1-3,
  verified against the upstream C++ golden test vectors (all input sizes
  0..=64, the SipHash reference vectors, and the streaming "cat"
  equivalence test).
- Backends: AVX2 and SSE4.1 on x86_64 (runtime-detected), NEON on aarch64,
  and a portable scalar fallback everywhere else, including big-endian and
  `no_std`.
